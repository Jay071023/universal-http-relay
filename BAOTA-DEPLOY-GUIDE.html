先看结论

这不是 PHP 项目。宝塔只负责服务器、Node.js 环境和进程守护；程序本身由 Node.js 运行。

8888业务 HTTP / 管理面板端口（可调整）
9001示例热更新端口，可换成任意未占用端口
安装时生成的随机Token远程更新 Token，安装时随机生成
部署结构主进程是 lb-server.js，远程更新/控制进程是 deploy-server.js。两个进程都要启动，缺一不可。

一、宝塔部署

推荐使用 PM2 配置文件启动两个进程，后续重启服务器也会自动拉起。

1

上传部署包

把 ZIP 上传并解压到：

/www/wwwroot/universal-http-relay

确认该目录下能看到 package.json、lb-server.js、deploy-server.js。

2

安装 Node.js 18 或 20

宝塔「软件商店」安装 Node.js 版本管理器，选择 Node.js 18+，然后检查：

node -v
npm -v

如果提示找不到 node，先在版本管理器中设置命令行默认版本，再重新打开终端。

3

安装依赖并初始化

cd /www/wwwroot/universal-http-relay
npm ci --omit=dev
node scripts/init-config.js

初始化命令会生成运行配置，并显示管理员密码和 Agent Token。请保存好，不要把真实 config.json 发给别人。

4

登录后台

后台只有密码，没有用户名。主服务启动后，用浏览器打开：

http://服务器IP:8888/

输入初始化时显示的 ADMIN_PASSWORD。如果配置了 Nginx 域名，就打开对应的域名地址；如果修改了 LB_PORT，把 8888 换成实际端口。

三个凭据不要混淆
ADMIN_PASSWORD：浏览器登录后台；AGENT_TOKEN：节点 Agent 连接认证；DEPLOY_TOKEN=安装时生成的随机Token：你这边远程上传、重启和控制服务器。浏览器登录成功后会保存 7 天会话。
5

创建远程控制配置

在项目根目录新建 .deploy.env，端口用 9001 举例：

DEPLOY_BASE_DIR=/www/wwwroot/universal-http-relay
DEPLOY_BIND=0.0.0.0
DEPLOY_PORT=9001
DEPLOY_TOKEN=安装时生成的随机Token
DEPLOY_SERVICE_MANAGER=pm2
DEPLOY_PROCESS_NAME=lb-server
安全边界热更新端口只提供认证后的文件更新、状态查询、健康检查和受控重启，不提供任意 Shell。必须把 9001 限制为你的固定 IP。
6

启动 PM2

cd /www/wwwroot/universal-http-relay
chmod 600 .deploy.env
pm2 start ecosystem.config.js
pm2 status
pm2 save
pm2 startup

pm2 startup 会输出一条系统命令，把它复制执行一次。之后重启服务器，两个 Node 进程会自动恢复。

7

检查健康状态

curl http://127.0.0.1:8888/healthz
pm2 logs lb-server --lines 50
pm2 logs deploy-server --lines 50

健康接口正常后，再配置网站反向代理或交付远程更新权限。

8

放行端口

业务端口
8888（按实际配置调整）
热更新端口
9001（按 DEPLOY_PORT 调整）
访问策略
9001 只允许你的固定公网 IP；不要对全网开放

二、你这边远程操作

在本地部署包目录执行，把“对方服务器IP”和端口换成实际值。

# 全量上传并自动重启（不上传目标机 config.json）
node upload.js --host 对方服务器IP --port 9001 --token 安装时生成的随机Token --all

# 查看状态
node control.js --host 对方服务器IP --port 9001 --token 安装时生成的随机Token status

# 健康检查
node control.js --host 对方服务器IP --port 9001 --token 安装时生成的随机Token health

# 重启主服务
node control.js --host 对方服务器IP --port 9001 --token 安装时生成的随机Token restart

# 重新加载受控服务
node control.js --host 对方服务器IP --port 9001 --token 安装时生成的随机Token reload
交互式更新Windows 可以运行 push.ps1，它会询问目标 IP、端口和 Token；端口留空默认 7879，Token 必须填写目标服务器生成的随机值。

修改 Token

首次确认部署正常后，建议把 .deploy.env 中的 Token 换成长随机字符串，然后：

cd /www/wwwroot/universal-http-relay
pm2 restart deploy-server --update-env
pm2 save

三、请求可靠性说明

针对接口需要 5～6 秒初始化的问题，程序按“等待当前请求完成”设计。

不会因 5 秒无响应就切下一个转发层默认最长等待 120 秒；只有真正超时、连接失败或客户端主动断开才结束当前请求。
超时可以调大管理面板的后端最长等待范围是 60～600 秒，适合更慢的初始化接口。

真实请求链路

1. 客户端发起
负载均衡器接收并保持当前请求
2. 选择节点
健康节点收到转发，不会因短暂初始化立即丢弃
3. 等待响应
持续读取完整 HTTP 响应，支持 Content-Length、chunked 和分片数据
4. 返回客户端
完整响应返回后结束本次请求
必须分清“不丢请求”不等于无限等待。上游断开、客户端主动取消或超过最大等待时间时，程序仍会结束并记录错误。

四、常见问题

pm2 status 没有 deploy-server

确认当前目录正确，执行 pm2 start ecosystem.config.js；仍失败就看 pm2 logs deploy-server --lines 100。

本地 control.js 连接不上

检查云安全组和宝塔防火墙是否放行热更新端口；确认 DEPLOY_BIND=0.0.0.0、端口和 Token 一致。不要把热更新端口放在只支持 HTTP 的普通反代后面。

网页能打开，但原始 TCP/FRP 不通

普通 Nginx HTTP 反代只适合网页和 HTTP 转发。原始 TCP/FRP 需要 Node 直接监听对应端口，或使用 Nginx stream/TCP 转发。

更新后服务没有起来

先执行 pm2 status 和 pm2 logs lb-server --lines 100。更新流程保留备份，可在确认故障后回滚；不要覆盖目标机生产 config.json。

如何只重启，不上传代码

使用 control.js ... restart；更新代码使用 upload.js ... --all。

把下面整段复制给他的 AI，再把部署包一起提供。AI 应先检查环境和目录，再执行命令，不要猜路径。

六、上线前检查

逐项打勾后再把服务器交给使用方。

交付建议首次部署可以使用远程 Token 安装时生成的随机Token 跑通流程；确认成功后立即更换随机长 Token，并把热更新端口限制为你的固定 IP。
